# Webhook formats

This page is the payload reference for webhook endpoints. For creating endpoints, retries, replay, destination rules and operating guidance, see [Webhooks](/guide/webhooks). For receiving mail, see [Inbound mail](/guide/inbound).

An endpoint has one format, fixed at creation:

| Format name | Payload | Signed | Event filter names |
| --- | --- | --- | --- |
| `thinpost` | Thinpost-native JSON | Yes (HMAC-SHA256, hex) | The outcome names below |
| `postmark` | Postmark-shaped JSON | No | `Delivery`, `Bounce`, `Open`, `SubscriptionChange`, `SpamComplaint` |
| `resend` | Resend-shaped JSON | Yes (Svix scheme) | `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.failed`, `email.opened`, `email.suppressed`, `email.complained` |
| `mailgun` | Mailgun-shaped JSON | Yes (Mailgun scheme) | `delivered`, `temporary_fail`, `permanent_fail`, `opened`, `unsubscribed`, `complained` |
| `thinpost_inbound` | Inbound message JSON | Yes (same as `thinpost`) | `inbound_received` only |

SendGrid webhooks are not available.

## HTTP request

Every delivery is an HTTPS `POST` with `Content-Type: application/json`. The format adds the headers below, then Thinpost adds any [HTTP authentication](/guide/webhooks#http-authentication) configured on the endpoint (Basic credentials and custom headers). Custom headers cannot replace a format header.

| Format | Event ID header | Signature headers |
| --- | --- | --- |
| `thinpost`, `thinpost_inbound` | `X-Thinpost-Event-ID` | `X-Thinpost-Timestamp`, `X-Thinpost-Signature` |
| `postmark` | `X-PM-Webhook-Trace-Id` | none |
| `resend` | `svix-id` | `svix-timestamp`, `svix-signature` |
| `mailgun` | none (the ID is `event-data.id` in the body) | none (the signature is in the body) |

The event ID is stable across retries and replays. Deduplicate on it.

A request is a success when the response status is 2xx. Redirects are not followed, the response body is ignored, and TLS 1.2 or later is required. Outbound event bodies are limited to 1 MiB with a 15-second request deadline. Inbound bodies are limited to 32 MiB with a 120-second deadline.

Test sends from the console add `X-Thinpost-Test: true` to provider-format and inbound requests. A native test body carries only `id`, `outcome` (`"test"`) and `occurred_at`, and has no test header.

### Signing

Secrets are generated by Thinpost, shown once, and never returned again.

| Format | Secret | Signature |
| --- | --- | --- |
| `thinpost`, `thinpost_inbound` | `tpwh_` followed by 43 base64url characters. The whole string, prefix included, is the key. | `X-Thinpost-Signature: v1=<hex>` where `<hex>` is the HMAC-SHA256 of `timestamp + "." + event_id + "." + raw_body`. `X-Thinpost-Timestamp` is Unix seconds. |
| `resend` | `whsec_` followed by the standard base64 of 24 random bytes. The key is the base64-decoded part after the prefix. | `svix-signature: v1,<base64>` where `<base64>` is the HMAC-SHA256 of `svix-id + "." + svix-timestamp + "." + raw_body`. `svix-timestamp` is Unix seconds. |
| `mailgun` | 64 hex characters. The whole string is the key. | The body's `signature` object: `timestamp` (Unix seconds as a string), `token` (50 hex characters, fresh for every request) and `signature`, the hex HMAC-SHA256 of `timestamp + token`. It does not cover `event-data`. |
| `postmark` | none | none. Use HTTP authentication. |

Verify against the raw request body bytes, compare in constant time, and reject stale timestamps. A verification example is in [Webhooks](/guide/webhooks#verify-signatures).

## Event mapping

Each delivery attempt, tracking hit and feedback report produces one Thinpost event with an outcome. A format receives an event only when it can represent it; other events are never queued for that endpoint.

### Classification

Provider formats classify an event from its outcome, SMTP code and the delivery state it produced:

| Class | Condition |
| --- | --- |
| Delivered | outcome `accepted` |
| Deferred | outcome `rejected` or `route_rejected` and the delivery is not failed (still retrying) |
| Permanent failure | outcome `null_mx` or `domain_not_found`; or outcome `rejected`, final, with SMTP code 500 or higher |
| Soft failure | outcome `retry_expired`; or outcome `rejected` or `route_rejected` that is final and not a permanent failure |
| Suppressed | outcome `suppressed` |

A rejection is final when its `delivery_state` is `failed`. When `delivery_state` is absent, a `rejected` outcome with code 500 or higher is treated as final. `route_rejected` happens before any recipient is presented, so it is never a permanent failure.

### Mapping table

| Thinpost outcome | `postmark` | `resend` | `mailgun` |
| --- | --- | --- | --- |
| `accepted` | `Delivery` | `email.delivered` | `delivered` |
| Deferred `rejected` or `route_rejected` | not sent | `email.delivery_delayed` | `temporary_fail` |
| Permanent failure | `Bounce` (`HardBounce`) | `email.bounced` (`Permanent`) | `permanent_fail` |
| Soft failure | `Bounce` (`SoftBounce`) | `email.bounced` (`Transient`) | `permanent_fail` |
| `suppressed` | not sent | `email.suppressed` | `permanent_fail` |
| `tracking_abandoned` | not sent | `email.failed` | `permanent_fail` |
| `preparation_failed` | not sent | `email.failed` | not sent |
| `hold_expired` | not sent | `email.failed` | not sent |
| `held`, `released`, `cancelled` | not sent | not sent | not sent |
| `opened` | `Open` | `email.opened` | `opened` |
| `unsubscribed` | `SubscriptionChange` | not sent | `unsubscribed` |
| `complained` | `SpamComplaint` | `email.complained` | `complained` |
| `uncertain`, `recipient_policy_denied`, `tracking_unavailable` | not sent | not sent | not sent |
| `bounce_received_unverified` | not sent | not sent | not sent |
| `clicked` | not sent | not sent | not sent |

`bounce_received_unverified` is an unauthenticated receipt and is never rendered as a provider bounce. `preparation_failed` and `hold_expired` are message-level and have no per-recipient Mailgun event. `held`, `released` and `cancelled` are the app's own hold actions and have no provider equivalent. Resend has no per-email unsubscribe event.

An endpoint with no event filter receives every event its format can represent. The `thinpost` format represents every outcome listed in [Native format](#native-format).

## Common rules

- **Omitted, not null.** A field Thinpost does not record is left out of the payload. It is never `null` or invented. Provider formats omit tags, metadata values, remote server response text, and client, operating system, geography, IP and user-agent details.
- **Fixed response text.** Where a provider carries remote server text, Thinpost writes a fixed sentence derived from the recorded SMTP code. It never quotes the remote server.
- **Message IDs.** The native `message_id` is 32 lowercase hex characters. Provider formats render the same ID in the shape that provider's send API returned: Postmark `MessageID` and Resend `data.email_id` as UUID text (hyphenated), Mailgun `message-id` as `<id>@<sender domain>` without angle brackets.
- **From address.** Provider payloads carry the sender only when it was recorded. Resend `data.from` and Mailgun `message.headers.from` use `Name <address>`, or the bare address when there is no display name. A name that contains anything beyond letters, digits, spaces and basic punctuation is sent as a quoted string. Names are never RFC 2047-encoded. Postmark `From` is the bare address.
- **Subjects and recipients.** Provider payloads include the recipient address. They include the subject unless the message uses Enhanced Protection, in which case the subject is never sent. No format includes message bodies. Recipients are the delivery's own address; for message-level events they are the message's To recipients only.
- **Timestamps.** Postmark uses `2006-01-02T15:04:05.0000000Z` form (seven fractional digits, UTC). Resend uses millisecond precision (`.000Z`). Mailgun `timestamp` is a decimal number of Unix seconds with microsecond precision. Native timestamps are RFC 3339 UTC.

## Native format

Native events carry identifiers, the outcome, the SMTP code and times. They never carry addresses, subjects or bodies.

```json
{
  "id": "evt_01example",
  "message_id": "0123456789abcdef0123456789abcdef",
  "delivery_id": "delivery-1",
  "attempt_id": "attempt-1",
  "outcome": "accepted",
  "smtp_code": 250,
  "occurred_at": "2030-01-15T12:00:00.123456Z",
  "delivery_state": "accepted",
  "message_id_header": "<0123456789abcdef0123456789abcdef@example.com>"
}
```

Headers:

```text
Content-Type: application/json
X-Thinpost-Event-ID: evt_01example
X-Thinpost-Timestamp: 1894000000
X-Thinpost-Signature: v1=<hex>
```

| Field | Type | Always present | Meaning |
| --- | --- | --- | --- |
| `id` | string | Yes | Event ID. Same as `X-Thinpost-Event-ID`. |
| `message_id` | string | Yes | The 32-character lowercase hex message ID. |
| `delivery_id` | string | No | The delivery (one recipient of the message). Absent for message-level events such as `preparation_failed` and the hold events. |
| `attempt_id` | string | No | The delivery attempt that produced the event. |
| `bounce_receipt_id` | string | No | Set on `bounce_received_unverified`. |
| `tracking_link_id` | string | No | Set on tracking events that reference a link. |
| `outcome` | string | Yes | One of the outcomes below. |
| `smtp_code` | integer | Yes | The SMTP reply code, or `0` when no SMTP reply applies. |
| `occurred_at` | string | Yes | RFC 3339 UTC time of the event. |
| `delivery_state` | string | No | The delivery state the event produced, such as `accepted` or `failed`. Absent when the event made no delivery transition. |
| `suppression_reason` | string | No | Only on `suppressed`: `hard_bounce`, `spam_complaint`, `unsubscribe` or `manual`. |
| `message_id_header` | string | No | The delivery's RFC 5322 `Message-ID`, with angle brackets. Absent when there is no delivery or no recorded sender domain. JSON-escaped like any string (`<` and `>` decode to angle brackets). |

Parsers that reject unknown JSON fields must accept `delivery_state`, `suppression_reason` and `message_id_header`.

### Outcomes

| Outcome | Meaning |
| --- | --- |
| `accepted` | The remote server accepted the message. |
| `rejected` | The remote server rejected it, temporarily or permanently. |
| `route_rejected` | A rejection during connection setup (greeting, EHLO or STARTTLS), before any recipient was presented. It does not by itself fail the delivery. |
| `null_mx`, `domain_not_found` | Decided locally from DNS. No SMTP was attempted and `smtp_code` is `0`. |
| `retry_expired` | The retry lifetime ran out before another attempt. `smtp_code` is `0`. |
| `suppressed` | The recipient is on the suppression list; nothing was sent. `smtp_code` is `0`. |
| `uncertain` | An attempt may or may not have reached the recipient and needs an operator. |
| `recipient_policy_denied` | The recipient was denied by policy before sending. `smtp_code` is `0`. |
| `preparation_failed` | The message could not be prepared. It has a `message_id` and no delivery. |
| `held`, `released`, `cancelled`, `hold_expired` | A message [submitted on hold](/guide/holding-messages) was accepted on hold, released, cancelled by its app, or expired without release. Each has a `message_id` and no delivery, and `smtp_code` is `0`. |
| `opened`, `clicked` | A tracking pixel or link was fetched. |
| `unsubscribed` | A recipient used one-click unsubscribe. |
| `complained` | A mailbox provider reported a spam complaint. |
| `bounce_received_unverified` | Mail arrived at a delivery's return path. It is not an authenticated bounce and must not by itself suppress an address. |
| `tracking_unavailable`, `tracking_abandoned` | A tracking-related hold, and an operator's decision to fail a held delivery. |
| `test` | Console test send only. Never queued and never in delivery history. |

## Postmark format

The payload is the Postmark webhook shape for the mapped record type. `MessageStream` is always `outbound`, `Tag` is an empty string and `Metadata` is an empty object. The request has no signature; the event ID is in `X-PM-Webhook-Trace-Id`.

### Delivery

```json
{
  "RecordType": "Delivery",
  "MessageStream": "outbound",
  "MessageID": "01234567-89ab-cdef-0123-456789abcdef",
  "Recipient": "user@example.net",
  "Tag": "",
  "DeliveredAt": "2030-01-15T12:00:00.1234560Z",
  "Details": "Accepted by the recipient's mail server (SMTP 250).",
  "Metadata": {}
}
```

`Recipient` is omitted when not recorded.

### Bounce

```json
{
  "RecordType": "Bounce",
  "MessageStream": "outbound",
  "Type": "HardBounce",
  "TypeCode": 1,
  "Name": "Hard bounce",
  "Tag": "",
  "MessageID": "01234567-89ab-cdef-0123-456789abcdef",
  "Metadata": {},
  "Description": "The server was unable to deliver your message (ex: unknown user, mailbox not found).",
  "Details": "Rejected by the recipient's mail server (SMTP 550).",
  "Email": "user@example.net",
  "BouncedAt": "2030-01-15T12:00:00.1234560Z",
  "DumpAvailable": false,
  "Inactive": false,
  "From": "sender@example.com",
  "Subject": "Your receipt"
}
```

| Field | Meaning |
| --- | --- |
| `Type`, `TypeCode`, `Name` | `HardBounce`, `1`, `Hard bounce` for a permanent failure. `SoftBounce`, `4096`, `Soft bounce` for a soft failure. |
| `Description` | A fixed sentence for the bounce type. |
| `Details` | A fixed sentence built from the SMTP code. |
| `Email` | The recipient. Omitted when not recorded. |
| `From`, `Subject` | Omitted when not recorded. `Subject` is never sent for Enhanced Protection messages. |
| `DumpAvailable`, `Inactive` | Always `false`. |

### Open

```json
{
  "RecordType": "Open",
  "MessageStream": "outbound",
  "FirstOpen": true,
  "MessageID": "01234567-89ab-cdef-0123-456789abcdef",
  "Metadata": {},
  "ReceivedAt": "2030-01-15T12:00:00.1234560Z",
  "Tag": "",
  "Recipient": "user@example.net"
}
```

`FirstOpen` is present only when Thinpost knows whether this is the first open.

### SubscriptionChange

```json
{
  "RecordType": "SubscriptionChange",
  "MessageID": "01234567-89ab-cdef-0123-456789abcdef",
  "MessageStream": "outbound",
  "ChangedAt": "2030-01-15T12:00:00.1234560Z",
  "Recipient": "user@example.net",
  "Origin": "Recipient",
  "SuppressSending": true,
  "SuppressionReason": "ManualSuppression",
  "Tag": "",
  "Metadata": {}
}
```

`ServerID` is omitted.

### SpamComplaint

```json
{
  "RecordType": "SpamComplaint",
  "MessageStream": "outbound",
  "Type": "SpamComplaint",
  "TypeCode": 100001,
  "Name": "Spam complaint",
  "Tag": "",
  "MessageID": "01234567-89ab-cdef-0123-456789abcdef",
  "Metadata": {},
  "Description": "The subscriber explicitly marked this message as spam.",
  "Details": "The recipient reported this message as spam.",
  "Email": "user@example.net",
  "From": "sender@example.com",
  "BouncedAt": "2030-01-15T12:00:00.1234560Z",
  "DumpAvailable": false,
  "Inactive": true,
  "CanActivate": false,
  "Subject": "Your receipt"
}
```

The abuse-report `Content` field is omitted. `Email`, `From` and `Subject` are omitted when not recorded.

## Resend format

The payload is `{ "type", "created_at", "data" }`. `created_at` is the event time. Headers are `svix-id`, `svix-timestamp` and `svix-signature`.

```json
{
  "type": "email.delivered",
  "created_at": "2030-01-15T12:00:00.123Z",
  "data": {
    "created_at": "2030-01-15T11:59:58.500Z",
    "email_id": "01234567-89ab-cdef-0123-456789abcdef",
    "from": "Sender Name <sender@example.com>",
    "to": ["user@example.net"],
    "subject": "Your receipt"
  }
}
```

| `data` field | Meaning |
| --- | --- |
| `created_at` | When the message was accepted by Thinpost. Omitted when not recorded. |
| `email_id` | The message ID as UUID text. |
| `from` | The sender. Omitted when not recorded. |
| `to` | The delivery's recipient, or every To recipient for message-level events. Omitted when none is recorded. |
| `subject` | Omitted when not recorded and for Enhanced Protection messages. |
| `bounce` | On `email.bounced` only. |
| `failed` | On `email.failed` only. |
| `suppressed` | On `email.suppressed` only. |

`email.bounced` carries:

```json
"bounce": {
  "message": "Rejected by the recipient's mail server (SMTP 550).",
  "subType": "General",
  "type": "Permanent",
  "diagnosticCode": ["smtp; 550"]
}
```

`type` is `Permanent` or `Transient`. `subType` is always `General`. `diagnosticCode` is present only when the SMTP code is above zero.

`email.failed` carries `"failed": { "reason": "tracking_abandoned" }`, `"failed": { "reason": "preparation_failed" }` or `"failed": { "reason": "hold_expired" }`.

`email.suppressed` carries `"suppressed": { "message": "The recipient is on the suppression list. No SMTP attempt was made.", "type": "OnAccountSuppressionList" }`.

`email.delivery_delayed`, `email.opened` and `email.complained` carry only the common `data` fields.

## Mailgun format

The body is `{ "signature", "event-data" }`. There are no signature headers.

```json
{
  "signature": {
    "timestamp": "1894000000",
    "token": "<50 hex characters>",
    "signature": "<64 hex characters>"
  },
  "event-data": {
    "event": "delivered",
    "id": "evt_01example",
    "timestamp": 1894000000.123456,
    "log-level": "info",
    "recipient": "user@example.net",
    "recipient-domain": "example.net",
    "message": {
      "headers": {
        "message-id": "0123456789abcdef0123456789abcdef@example.com",
        "from": "Sender Name <sender@example.com>",
        "subject": "Your receipt"
      }
    },
    "delivery-status": {
      "code": 250,
      "message": "Accepted by the recipient's mail server (SMTP 250)."
    },
    "domain": { "name": "example.com" },
    "tags": [],
    "user-variables": {}
  }
}
```

| `event-data` field | Meaning |
| --- | --- |
| `event` | `delivered`, `failed`, `opened`, `unsubscribed` or `complained`. Both `temporary_fail` and `permanent_fail` filter names produce `event: "failed"`; `severity` tells them apart. |
| `id` | The Thinpost event ID. |
| `timestamp` | Event time, Unix seconds with microsecond precision. |
| `log-level` | `info`, except `warn` for `complained` and temporary failures and `error` for permanent failures. |
| `severity` | `temporary` or `permanent`. `failed` events only. |
| `reason` | `failed` events only. `bounce` for a permanent failure with SMTP code 500 or higher. `suppress-bounce`, `suppress-unsubscribe` or `suppress-complaint` for a suppressed recipient. `generic` otherwise. |
| `recipient`, `recipient-domain` | The recipient and its lowercase domain. Omitted when not recorded. |
| `message.headers.message-id` | `<message id>@<sender domain>`, without angle brackets. The bare message ID when no sender domain is recorded. |
| `message.headers.from`, `.subject` | On `delivered`, `complained` and `failed` events only, when recorded. `subject` is never sent for Enhanced Protection messages. |
| `delivery-status` | On `delivered` (`code` 250) and `failed` events. `code` is omitted when the SMTP code is zero. `message` is a fixed sentence. `bounce-type` is `hard` for a permanent failure with code 500 or higher. |
| `domain.name` | The sender domain. Omitted when not recorded. |
| `tags`, `user-variables` | Always empty. |

Suppressed recipients use these `reason` and `delivery-status.code` values:

| `suppression_reason` | `reason` | `delivery-status.code` |
| --- | --- | --- |
| `unsubscribe` | `suppress-unsubscribe` | 606 |
| `spam_complaint` | `suppress-complaint` | 607 |
| `hard_bounce`, `manual` | `suppress-bounce` | 605 |

`opened` and `unsubscribed` events carry no `message.headers.from`, `subject` or `delivery-status`.

## Inbound mail payload

The `thinpost_inbound` format delivers mail an app receives at its receiving domains. It represents only the event `inbound_received`. It is signed and sent exactly like the native format (headers `X-Thinpost-Event-ID`, `X-Thinpost-Timestamp`, `X-Thinpost-Signature`). One request is sent for each envelope recipient and each enabled inbound endpoint, and its event ID is stable across retries.

```json
{
  "id": "evt_01inbound",
  "outcome": "inbound_received",
  "occurred_at": "2030-01-15T11:59:59.25Z",
  "app_id": "app-1",
  "inbound": {
    "id": "11112222333344445555666677778888",
    "received_at": "2030-01-15T11:59:59.25Z",
    "recipient": {
      "address": "reply+ticket-42@mail.example.com",
      "local_part": "reply+ticket-42",
      "domain": "mail.example.com",
      "tag": "ticket-42"
    },
    "envelope": {
      "mail_from": "bounces@sender.example",
      "rcpt_to": ["reply+ticket-42@mail.example.com", "other@mail.example.com"],
      "client_ip": "198.51.100.7",
      "helo": "mail.sender.example",
      "tls": { "version": "TLS1.3", "cipher": "TLS_AES_128_GCM_SHA256" }
    },
    "headers": {
      "from": [{ "name": "Sender", "address": "sender@sender.example" }],
      "to": [{ "name": "Reply", "address": "reply+ticket-42@mail.example.com" }],
      "cc": [],
      "reply_to": [],
      "subject": "Re: Your receipt",
      "date": "Tue, 15 Jan 2030 11:59:50 +0000",
      "message_id": "<reply-1@sender.example>",
      "in_reply_to": "<0123456789abcdef0123456789abcdef@example.com>",
      "references": ["<0123456789abcdef0123456789abcdef@example.com>"],
      "auto_submitted": "",
      "header_list": [
        { "name": "Authentication-Results", "value": "mail.example.com; spf=pass smtp.mailfrom=sender.example; dkim=pass header.d=sender.example; dmarc=pass header.from=sender.example" },
        { "name": "Received", "value": "from mail.sender.example ([198.51.100.7]) by mail.example.com with ESMTPS id 11112222333344445555666677778888; Tue, 15 Jan 2030 11:59:59 +0000" },
        { "name": "Subject", "value": "Re: Your receipt" }
      ]
    },
    "text": "Thanks, that works.",
    "html": "<p>Thanks, that works.</p>",
    "omitted": [],
    "raw": "<base64 of the message>",
    "authentication": {
      "spf": { "result": "pass", "domain": "sender.example", "identity": "mailfrom" },
      "dkim": [{ "result": "pass", "domain": "sender.example" }],
      "dmarc": { "result": "pass", "domain": "sender.example", "policy": "reject" },
      "arc": { "present": false, "evaluated": false }
    },
    "correlation": {
      "matched": true,
      "message_id": "0123456789abcdef0123456789abcdef",
      "delivery_id": "delivery-1",
      "header": "in_reply_to",
      "from_matches_recipient": true
    },
    "classification": {
      "auto_submitted": false,
      "delivery_status_report": false,
      "feedback_report": false
    }
  }
}
```

| Field | Meaning |
| --- | --- |
| `id`, `outcome`, `occurred_at`, `app_id` | The envelope. `outcome` is always `inbound_received` and `occurred_at` is the receipt time. |
| `inbound.id`, `inbound.received_at` | The stored message ID and receipt time. The same for every recipient's event. |
| `recipient` | This event's address: `address` as given, `local_part`, `domain` (lowercase) and `tag`, the text after the first `+` of the local part (empty when there is none). |
| `envelope` | `mail_from` (empty for the null sender), `rcpt_to` (every envelope recipient), `client_ip`, `helo` and `tls` (`version`, `cipher`). `tls` is `null` when the message did not arrive over TLS. `client_ip` and `helo` are omitted when not recorded. |
| `headers` | Parsed from the delivered message. `from`, `to`, `cc` and `reply_to` are lists of `{name, address}` with RFC 2047 names decoded and `name` omitted when empty. `subject` is decoded. `references` is a list. An absent header is an empty string or list. |
| `headers.header_list` | Every header field in order as `{name, value}`, unfolded, including the two fields Thinpost prepends. At most 200 fields; values are cut at 1,024 bytes. |
| `text`, `html` | The first text and HTML body parts that are not attachments, decoded to UTF-8. Omitted when the message has no such part. |
| `omitted` | Names of fields left out: `text`, `html`, or `headers`. Empty when nothing was left out. |
| `raw` | The message as standard base64, described below. |
| `authentication` | `spf`, `dkim` (a list), `dmarc` and `arc`. SPF, DKIM and DMARC are reported, not enforced. `arc` is always `{"present": <bool>, "evaluated": false}`. |
| `correlation` | `{"matched": false}` when the message does not reference one of the app's messages. When matched: `message_id`, `delivery_id` (omitted for a message-level match), `header` (`in_reply_to` or `references`) and `from_matches_recipient` (omitted when it could not be determined). |
| `classification` | `auto_submitted` (an `Auto-Submitted` header other than `no`), `delivery_status_report` and `feedback_report` (a top-level `multipart/report` of that type). |

Parsing is bounded. A decoded body larger than 1 MiB, or in a charset Thinpost cannot decode, is left out and named in `omitted`. Both bodies are left out when a multipart part header runs over 64 KiB without a blank line. `headers` is left out when the received header block is over 64 KiB. Parsing allows a MIME depth of 5 and 100 parts. There is no attachment list: attachment parts appear only inside `raw`.

### The raw field

`raw` is the stored message exactly as received, with two fields prepended by Thinpost: an `Authentication-Results` field built from the recorded SPF, DKIM and DMARC results with the receiving host as its authserv-id, and a `Received` field for this hop. Any `Authentication-Results` field of the incoming message that claims the same authserv-id is removed first, so a sender cannot present results as if Thinpost had checked them. Fields from other servers are left as received. Trust the prepended field and the `authentication` object, never a later `Authentication-Results` that names a different host.

### Size and test sends

The stored message is at most 10 MiB, so a request is at most about 14 MiB of base64 plus two bodies of up to 1 MiB each. Your endpoint must accept requests of that size and answer within 2 minutes.

Correlation is a claim made by the message's headers, not authentication. To trust a reply as coming from the person you wrote to, require `correlation.from_matches_recipient` and a DMARC `pass`.

The console's test send posts a fixed synthetic message to `inbound-test@example.com` with `X-Thinpost-Test: true`.
